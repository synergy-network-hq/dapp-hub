Native end-to-end qualification requires an APQE-verified NodeNetwork release bound to Portal's first-party native extension, and a VPN control-plane issuer for the isolated target. Component checks and public observations do not establish membership, startup authorization or finality.

Permission-scope follow-up: target controller remounts when effective inspection permission changes, immediately dropping displayed prior-scope results and invalidating late response publication through its existing unmount guard. The module-level mutation latch remains across remounts. This does not cancel native transport or establish native grant-revocation acceptance.

Public status response follow-up: node/PoSy/sync reads reject null/scalar/array payloads independently, preserving successful sibling observations and showing failed-source errors. An HTTP/RPC success alone does not establish a usable status object or managed-host readiness.

Controller capability parsing rejects non-array/oversize tables, missing/duplicate operation entries and non-Boolean availability; blocker presentation accepts bounded plain text only. These frontend denials do not replace native validation or establish host authorization.

This distinguishes configured connections but is not host identity proof or a signed plan. Actual controller compilation is checked in isolation; full command/dialog runtime remains engine-blocked.

Bootstrap review now includes the validated node name and SHA-256 of the selected normalized operator public-key text. The fingerprint is a local comparison aid, not independent key authorization or APQE proof. No key material is journaled; native dialog/runtime acceptance remains unverified.

Saved-target recovery distinguishes missing/null records from unreadable/unsupported records. 2026-11-17 engineering formation authorization: the native file selector accepts only an exact document whose SHA-256 was independently compiled into a debug Portal using `SYNERGY_NODENETWORK_QUALIFICATION_AUTHORIZATION_SHA256` or the comma-separated `SYNERGY_NODENETWORK_QUALIFICATION_AUTHORIZATION_SHA256S` set (at most five distinct initial host documents; the single pin, if also set, must belong to that set). Production builds have no authorization path. This approval is separate from the APQE-signed Hub release and approved master pin; it is not a public policy issuer, Genesis signature, admission or stake proof.

The bounded document uses `version:1`, profile `nodenetwork-isolated-formation-authorization-v1`, exact `target` (`kind`, `host`, effective `port`, lowercase `root`, administrative SSH `host_key`, and `machine_id_sha256`: remote uses its host key and null machine hash; local uses a pinned SHA-256 of exact `/etc/machine-id` bytes and null host key), `release_id`, `manifest_sha256`, `network_id`, numeric `chain_id`, `node_name`, consecutive `sequence`, `expires_at` (at most one hour), `artifacts` (fixed relative input name → SHA-256), `requests` (`operation`, exact canonical `request_sha256`), and nullable three-file `genesis_pins`. The native selector reads matching fixed-name artifacts beside the document. It never returns one-use VPN input to JavaScript. Formation context, complete public commissioning inputs and optional one-use VPN enrollment are staged only within the controller namespace. Signed Genesis staging and existing native membership/custody verification remain mandatory.

The embedded master validates the enrolled engine and approved master/network, holds the lifecycle lock, atomically exchanges the controller's policy, inputs and one-use grants, and records the authorization digest/sequence. Grant consumption remains before dispatch. Reconciliation of an already applied document never recreates consumed grants; an exact exchanged predecessor can be removed after a verified interrupted publication. The UI offers `Read or reconcile staged authorization` without dispatching a mutation. An expired document cannot create new grants. Pending earlier grants or enrollment and conflicting inputs block staging. Formation, artifact, configuration and custody authorization changes require the node stopped. A debug native-confirmed continuation may exchange only one exact stop/restart grant while active, with no artifact or network-pin changes. This does not perform live repair or grant production approval. Actual application-driven staging, fresh Genesis issuance/approval, automatic authorized VPN issuance and complete local/remote lifecycle qualification remain required; a source build or scratch-file test does not establish those outcomes.

Fresh engineering Genesis now has separate native preparation, review/signing and public-export operations. On a stopped enrolled formation coordinator, the app selects a folder with `recipe.json` (at most 1 MiB) and `registration-1.json` through `registration-5.json` (each at most 128 KiB). The master supplies fixed registration paths and verifies the existing formation proofs and exact recipe membership; renderer paths and private input are not accepted. `network_formation_prepare` creates one managed encrypted APQE authority custody and records the exact request. `network_formation_status` re-verifies durable custody and original inputs without regeneration. `network_formation_sign` separately reviews the exact unsigned Genesis, authority, public-root and five-validator digests and requires its own one-use host grant. Interrupted creation/signing is never replayed. Only the three independently verified signed public artifacts can be exported; the raw public root is transported as canonical base64. Stage B still requires independent exact pins and verified membership on each host.

This is an isolated engineering network creation path, not production authorization or a stake/consensus-eligibility claim. An independently compiled initial host document establishes the engineering host/master/formation scope. Thereafter, native-confirmed continuations bind its initial receipt, exact current parent receipt, same host/master/network/formation, consecutive sequence, five-minute expiry and one exact request. Freshly generated review and Genesis hashes are not renderer self-authorization: the app stores only the signed PUBLIC export and exact native review, recontacts its original approved coordinator through its pinned SSH identity and current APQE-verifying keytool, compares exact export/root/scope, and verifies the receiving host prepared identity before Stage B pin adoption. The receiving master still verifies all Genesis, authority and membership signatures. No custody or unlock material enters this cache. Interrupted continuation intents reconcile only an exact target receipt; they are never blindly resent. Expired, unconsumed grants are retired only inside the next atomic policy exchange after matching their original authorization receipt; consumed grants are never recreated. A consumed non-lifecycle request cannot be regranted; a repeated lifecycle action needs a new explicit confirmation and sequence. New software-version staging/approval is a separate release qualification; this continuation cannot change its approved master. Native unit/controller tests do not establish actual Portal host provisioning or five-validator acceptance.
