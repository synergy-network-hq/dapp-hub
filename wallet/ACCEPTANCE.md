Account reads reject null/scalar/array top-level responses. No frontend scope marker, chain ID, matching balances or source build establishes APQE/session proof, spendability or finality. See UPSTREAM.md for pinned design provenance and current crypto restrictions. Release descriptor remains null.

Next sequence: validate qualified native custody and upstream session proofs with the supported phone protocol; obtain canonical transaction and broadcast/finality contracts before enabling writes; integrate supported cursor/inventory/media APIs without inventing fields; run connected and native acceptance on the migrated sources. Preserve the upstream design and the host SDK boundary.

Widget response follow-up: the dashboard account read now rejects null, scalar and array response shapes like the full Wallet view. Unsupported payloads produce an unavailable state rather than an inferred empty history. Source builds do not establish connected/native acceptance.

Oversized originals remain untouched and reads/writes report unavailable instead of inferring empty data. Browser storage-failure/full acceptance remains open.

Unsupported-schema preservation: unknown contact fields or unknown provisioning-envelope fields now make the existing record unsupported rather than allowing a later save to silently discard those fields. Original storage is retained; reviewed migration/recovery remains required.

Balance presentation now explains Atlas fallback-zero ambiguity identified in the pinned backend review. Numeric agreement is not called successful dual-read verification. The balance widget links to separate Wallet RPC/index observations. Connected/browser/native availability acceptance remains open.

Transaction status follow-up: W06 can check a supported hash on demand through the existing `synergy_getTransactionByHash` read. The selected index record must include the connected account. The lookup checks RPC chain ID first and accepts results only for the requested hash, chain 1266, network `testnet` and connected account. The parser follows the transaction projection at testnet-v3 commit `05610db7eb1eaa582caec0adf0c7967c820d5e34` in `runtime/src/rpc/rpc_server.rs`. It distinguishes a missing result, a pool observation and a block observation. A difference with the indexed block is shown without inferring a reorganization, dropped transaction or finality. A public gateway probe with a synthetic hash returned JSON-RPC `result: null`. No positive live transaction or connected Wallet was used.

The scoped Portal desktop component tests verify on-demand dispatch, exact block height, recheck replacing the prior result, selected-hash change invalidating pending work, and hash, network, chain, account or unsafe-height rejection. Clipboard execution and receipt, reorganization and finality verification remain open. The explorer action is pending Wallet external-link consent.

Activity type follow-up. W05 can filter current-page and fallback rows by the reported hash family. The hash rules come from `Transaction::hash` in testnet-v3 at commit `05610db7eb1eaa582caec0adf0c7967c820d5e34`, which emits `syntxn-` for regular transactions and `synxxn-` for cross-chain transactions. Wallet requires a valid digest before assigning either family. Untyped or malformed hashes remain unclassified. The filter works with existing direction, date, search and indexed-status controls. Account-history v1 has no transfer-asset classification. The native amount field alone cannot distinguish token activity or establish provenance. Portal's focused Wallet Activity tests cover filter composition, visible row type, selecting a matching transaction and unclassified rows in the recent fallback.

Token inventory follow-up. The pinned Atlas owner at `3fb8f87` returns `address`, `source: atlas_token_balances`, `items` and `total` from `/wallets/:address/token-balances`. Wallet checks the reported account and row count before displaying canonical data. Earlier array and array-wrapper formats remain readable with unqualified units and an explicit missing-account message when the response omits the account. A public read with a synthetic address returned the matching account, an empty item array and total zero.

W03 search includes native STS token address and ID as well as SynQ contract address. Source filters separate STS indexed holdings and SynQ initial allocations. Wallet computes exact token units from a bounded atomic string and the reported decimals, without using Atlas's rounded display quantity as a fallback. It labels STS creation and SynQ deployment blocks as such. Atlas can suppress an STS backend lookup failure and SynQ initial allocations do not track later contract activity. An empty reply means the endpoint returned no rows. Token ownership, spendability, verified provenance and complete inventory remain unproven. Focused Portal component tests cover exact precision, source filtering, STS identity without a contract, null or unsafe amounts, the canonical account boundary and legacy display. No connected account was used.

Contacts follow-up. W11 uses Portal dialogs for the Add and Edit drawers and the existing removal review. The address book keeps its chain 1266 storage key and schema. Refreshes and sibling-window storage events update saved rows while the open editor keeps its draft. An outdated edit or removal must be reviewed with the current data before saving. Malformed storage remains intact. The copy action rereads storage and refuses a changed or unavailable contact.

Seven scoped Portal component cases covered drawer focus and return, checksum-valid duplicate refusal, storage write failure and retry, draft retention after a simulated sibling-window event, a stale copy and removal before that event, successful reviewed removal and focus recovery, and malformed storage retention. Tests used synthetic contact addresses and a clipboard spy. Clipboard execution on the device, actual multi-window contention, and recipient draft integration with a qualified signing path remain open.

Connections follow-up. W12 remains reachable with no phone connected, no Wallet read consent or an unsupported selected chain. The recovery view exposes Portal navigation and the selected network context. Public account and session details, effective grant rows and data requests remain behind the existing Wallet read gate. With consent, matching Portal session timing and inactivity settings describe local policy. Mobile version and approved phone scopes are unavailable from the adapter. The grants table uses installed application versions and the host's current-context check. A transaction-request grant is described separately from Wallet signing and submission, which remain unavailable.

Five focused Portal component cases cover the production Wallet entry point in disconnected, denied and incompatible-network contexts, navigation to host repair screens, withheld account reads, matching session timing, installed-app scope projection and revoked-read display cleanup. They use synthetic local host context. Native phone/session lifecycle, qualified remote acknowledgements and signing remain open.
